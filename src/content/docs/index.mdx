<div class="ldg-section">
  <p class="ldg-eyebrow">The Linux difference</p>
  <h2 class="ldg-title">No single vendor. One set of contracts.</h2>
  <p class="ldg-lede">Linux gives you a small number of open standards, several excellent toolkits, and users who expect to stay in control. The constraints are real: no single vendor, no single store, no single design authority. The result is software that can be faster, more focused, and more deeply integrated than a one-size-fits-all platform allows.</p>

  <div class="ldg-grid-3">

<div class="ldg-section">
  <p class="ldg-eyebrow">The target model</p>
  <h2 class="ldg-title">Linux has no default. This guide does.</h2>
  <p class="ldg-lede">A vendor-controlled platform can define one screen, one toolkit and one store. Linux cannot. This guide closes the gap with a small, evidence-based target set: a distribution, a desktop, a default stack, a HIG and a packaging path for each.</p>

  <div class="ldg-grid-3">
    <div class="ldg-card ldg-card--feature">
      <h3>Reference targets</h3>
      <p><strong>Ubuntu 26.04 LTS + GNOME</strong> for GTK/libadwaita, and <strong>Fedora 45 KDE + Qt</strong> for Qt/Kirigami. These get the full golden path and quality gates.</p>
      <p class="ldg-after"><a class="ldg-textlink" href="/targets/">See the target matrix <span aria-hidden="true">→</span></a></p>
    </div>
    <div class="ldg-card ldg-card--cyan">
      <h3>Validation targets</h3>
      <p>Fedora Workstation + GNOME and Arch Linux catch upstream GTK, libadwaita and Qt drift before your users do. They are test environments, not support promises.</p>
    </div>
    <div class="ldg-card ldg-card--lime">
      <h3>Compatibility target</h3>
      <p>Debian 13 keeps the conservative, long-support path visible — with older GTK/Qt libraries and Flatpak for apps that need a newer stack.</p>
    </div>
  </div>
</div>

<div class="ldg-section">
  <p class="ldg-eyebrow">The four contracts</p>
  <h2 class="ldg-title">Native is a promise, not a theme.</h2>
  <p class="ldg-lede">Every quality you want — speed, polish, reliability, that indefinable “it belongs here” feeling — comes from honoring four contracts with the platform.</p>

  <div class="ldg-grid-4">
    <a class="ldg-contract" href="/platform/wayland/">
      <span class="ldg-num">01</span>
      <h3>Display</h3>
      <p>Render on Wayland. Handle scaling, input methods and screen capture through the compositor — never by reaching around it.</p>
      <span class="ldg-contract-link">Wayland &amp; display <span aria-hidden="true">→</span></span>
    </a>
    <a class="ldg-contract" href="/platform/integration/">
      <span class="ldg-num">02</span>
      <h3>Desktop</h3>
      <p>Use the host's widgets, HIG, icons, notifications, file dialogs and settings. Integrate through D-Bus and XDG portals.</p>
      <span class="ldg-contract-link">System integration <span aria-hidden="true">→</span></span>
    </a>
    <a class="ldg-contract" href="/platform/xdg/">
      <span class="ldg-num">03</span>
      <h3>Data</h3>
      <p>Store config, state, cache and user data where the XDG spec says. Write atomically. Never assume the app owns the home directory.</p>
      <span class="ldg-contract-link">The XDG contract <span aria-hidden="true">→</span></span>
    </a>
    <a class="ldg-contract" href="/platform/packaging/">
      <span class="ldg-num">04</span>
      <h3>Distribution</h3>
      <p>Ship a reproducible build with valid AppStream metadata, minimal permissions and an update path you don't have to hand-roll.</p>
      <span class="ldg-contract-link">Packaging &amp; distribution <span aria-hidden="true">→</span></span>
    </a>
  </div>
</div>
